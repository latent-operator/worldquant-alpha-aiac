# 从落库 trace 恢复并复盘

## 先确定在看什么

按用户指定 task/run 查询；没有 ID 时从近期任务和当前研究目标匹配，多个候选无法区分才询问。
读取 run 配置快照、trace、分页后的全部 Alpha 和原生分析/轮次摘要。记录观察时间、实际版本（若有）、地区/股票池/设置。
旧 bounded run 用兼容只读报告；原生 run 不应被套上旧 REQUESTED/ACCEPTED 状态模型。
指标和 trace 缺失时说明缺失，不能从 HTTP 200、task.status 或聊天记录推定结果。

## 复盘顺序

1. **执行是否完整**：多少候选生成、验证淘汰、提交、明确返回、失败/不确定；没有提交计数证据就不编造。
   核对 run 状态、最后 trace 时间和对应 Worker 日志；排队与实际消费分开。
2. **要求是否兑现**：读取实际参数和 iteration，核对假设、字段、设置、预算/停止约定。
   原生 API RUNNING 不证明还在计算；超过时间限额、Worker 中断和数据集提前停止分别解释。
3. **质量是否达标**：保留原始质量标签和失败检查；比较同设置下 Sharpe、Fitness、turnover、margin、地区及风险中性表现。
   margin 是每交易金额收益；内部 test 段不是独立 OS，数据覆盖率不是 PIT 证明。
   已保存 PASS 与最终 PPA_READY 分别报告，缺失的相关性/最终验收证据不推为通过。
4. **失败归因**：区分元数据/字段错误、生成/语法错误、平台拒绝/超时、持久化或运行问题，以及经济机制弱。
   不将一条错误响应写成“这个机制无效”，也不把全批 FAIL 归咎于基础设施。
5. **有没有实际换方向**：比较原生策略 trace 与后续生成/回测表达式。只有建议但没有下一轮执行证据时明确说未执行。
   多次同机制失败时建议换解释/数据；必要时针对失败项再用 Playwright 查社区，不以帖子评价覆盖真实回测。
6. **下一步**：给出继续、换机制或停止的建议及理由，注明哪些结论尚不确定。
   用户只查结果时不创建任务；用户要求继续时返回需求整理流程，使用已有授权而非重复要求批准。

紧凑输出包含：观察时间、task/run、完成程度、关键指标/失败项、策略变化证据、建议及缺口。
复盘本身不改质量标签或请求状态。原生后台已有的反思保存在其 trace/知识库；本 Skill 从事实重建解释，不新增研究台账或后台回顾作业。

## 速度问题

分别报告提交时间、WQ 结果时间（可得时）和本地落库时间；按实际时间窗算吞吐。
不能把落库速度直接称为 WQ 计算速度，不能仅因 Worker 在线就断言回测在推进。
比较原生批量大小、实际在途数量和限流记录，不从账户宣称额度推导已达到最大吞吐。
